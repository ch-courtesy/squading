## 무엇을 하는 게임인가

열여섯 명 중 **한 명**만 조종한다. 나머지 열다섯은 알아서 싸운다 — 사거리에 들어온 적을 알아서 쏘고, 알아서 자리를 잡는다.

그래서 이 게임에서 당신이 하는 일은 **쏘는 것이 아니라 서는 것이다.**

- 분대가 쫓아갈 적은 **당신이 서 있는 자리**를 기준으로 정해진다. 물러서면 싸움이 줄고, 파고들면 늘어난다.
- 앞열의 돌격병은 **밀고 들어갈 때만** 제 위력을 낸다. 가만히 서 있으면 소총병보다 약하다.
- 쓰러진 동료 옆에 멈춰 서느냐가 **그 사람이 다음 판에 있느냐**를 가른다.

**조종하던 사람이 쓰러져도 판은 끝나지 않는다.** 가장 가까운 병사가 지휘를 이어받고, 당신은 그 사람이 된다. 열여섯 명 모두 이름이 있고, 죽으면 명단에 남는다.

그렇게 일곱 판을 이어 달린다. **살아남은 사람도, 모은 강화도, 잃은 사람도 판을 넘어 이어진다.** 판이 바뀔 때 돌아오는 건 체력뿐이다.

## 이 프로젝트가 실제로 어떻게 만들어졌나

Codex를 "코드를 대신 쳐주는 도구"로 쓰지 않았다. **설계를 판정하는 자리**에 썼고, 판정의 근거는 사람의 감이 아니라 **매번 새로 돌린 측정**이었다.

방식은 이렇다.

1. **스펙이 권위다.** `docs/superpowers/specs/`의 전투 스펙 613줄과 캠페인 스펙 206줄이 규칙의 유일한 출처다. 코드는 스펙을 §번호로 인용하고, 스펙이 바뀌면 버전이 오른다(§1.11은 v19, §1.13은 v2, §1.4.1은 v22까지 갔다).
2. **무엇이 재미인지를 문장으로 적고, 봇이 그걸 검증한다.** "가만히 있는 플레이는 전멸한다", "도망만 다니면 이기지 못한다", "한자리에 눌러앉으면 이기지 못한다", "구조를 포기하면 최종 생존이 세 명 이상 손해다". 성향이 다른 봇 여덟이 서로 다른 판 여덟 개를 끝까지 플레이해 매번 다시 확인한다.
3. **설계 변경은 재보고 채택한다.** 아이디어가 좋아 보여도 위 검증이 깨지면 버린다.
4. **테스트가 진짜 무는지도 잰다.** `scripts/mutate.mjs`가 규칙을 96가지 방식으로 고의로 망가뜨리고, 테스트가 전부 잡는지 확인한다. **96/96.**

### 측정이 설계를 뒤집은 기록

이 README에서 가장 정직한 부분이다. **내 추론은 반복적으로 틀렸고, 매번 측정이 이겼다.**

| 내가 생각한 것 | 측정 결과 |
|---|---|
| 엄폐 시스템이 위치 선택을 만든다 | 아레나 504칸 중 **엄폐가 유효한 칸이 0개**였다. 규칙째로 삭제 |
| 로스터를 키우면 선형으로 버틴다 | 몸당 피해가 **26배**로 줄었다. 선형이 아니라 제곱 법칙 |
| 근접 병종은 수치만 잘 잡으면 된다 | 약하게 잡으면 분대 화력이 죽고, 세게 잡으면 가만히 있는 플레이까지 같이 이긴다. **둘을 동시에 만족하는 수치 조합이 없다** |
| 원거리 병종에 회피를 주면 된다 | 봇이 알아서 피하는 형태를 **다섯 가지** 만들어 봤고 전부 검증을 깼다. 도망만 다니는 플레이가 **여덟 판을 다 이겼다** |
| 적을 세게 만들어 상쇄하면 된다 | 못하는 플레이를 죽일 만큼 세게 하면 **잘하는 플레이가 먼저 죽는다.** 사이에 여지가 없다 |

여기서 나온 **구조적 발견 하나**가 이 게임의 설계를 지배한다:

> 분대는 스스로 싸운다. 그러므로 **분대를 강하게 만드는 모든 것은 아무것도 안 하는 플레이도 똑같이 강하게 만든다.**

그래서 돌격병의 강한 타격도, 소총병의 회피도 **플레이어가 방향키를 쥐고 싸움 쪽으로 밀고 있을 때만** 나온다. 수치가 아니라 조건이 병종을 만든다.

### 돌아가는데 보이지 않던 것들

가장 자주 나온 결함이 이 부류였다. 규칙은 멀쩡히 동작하는데 **화면이나 귀에 닿지 않는** 것들이다.

- **돌격병이 네 번의 작업 동안 소총을 들고 있었다.** 사거리도, 피해도, 돌격 조항도 전부 돌고 있었다. 다만 그 병종을 렌더러에 전달하는 값이 없어서 화면에는 소총병으로 그려졌고, 코앞에서 클리버를 휘두르며 **총구 연기**를 뿜었다.
- **배경음악이 노트북에서 안 들렸다.** 55Hz 베이스를 220Hz에서 잘라낸 편성이었는데, 그건 **작은 스피커가 통째로 버리는 대역**이다. 모든 코드가 돌고 모든 테스트가 통과하는데 음악은 없었다. 실제 파형을 뽑아 스피커가 받는 몫만 재서 고쳤다(옛 편성 `0.09`, 새 편성 `0.44` — 전체 음량은 거의 같다. **음량 문제가 아니었다**).
- **테스트가 읽던 비율 `3`은 사실 `0 ÷ 0`이었다.** 두 값이 각각 `5.6e-15`, `1.9e-15`, 그러니까 계측이 아무것도 재지 못하고 있었다. 계측을 고치니 `1.250` — 테스트가 요구하던 구간의 정중앙이었다. **테스트는 내내 옳았다.**

셋 다 같은 교훈이다. **"테스트가 통과한다"와 "사람이 알아챈다"는 서로 다른 주장이다.**

## 기술

- **TypeScript + Vite**, 런타임 의존성은 Three.js와 Phaser뿐
- **결정론적 고정 스텝 시뮬레이션** — 30Hz, 2700틱, 용도별로 분리한 난수 스트림, 상태 전체의 해시. 같은 판을 같은 입력으로 다시 돌리면 브라우저에서든 헤드리스에서든 **완전히 같은 결과**가 나온다. 브라우저 테스트가 매번 자기 플레이를 헤드리스로 재생해 대조한다
- **규칙과 표시의 분리** — 규칙 쪽은 렌더러도 오디오도 모른다. 화면과 소리는 규칙이 내보낸 투영본만 읽고 아무것도 되돌려 쓰지 않는다. 오디오 파일을 통째로 지워도 판의 해시는 그대로다
- **유도 가능한 값은 상태에 두지 않는다** — 다른 값에서 계산되는 것은 저장하지 않는다는 규율이고, 상태 객체의 키 목록 자체가 테스트로 고정돼 있어 몰래 늘어날 수 없다
- **Three.js 2.5D 디오라마** — 정사영 카메라, 유닛당 드로우콜 4개 상한, 정점 셰이더 스켈레탈 리그(8관절, 병합 지오메트리 1개)
- **오디오는 합성** — 효과음 전부가 WebAudio 오실레이터·필터·노이즈다. 외부 파일은 BGM 하나뿐

## 아직 못 한 것

위의 숫자들과 같은 방식으로 잰 것이고, 결과가 목표에 못 미친 것들이다.

- **잘 서는 것과 아무 데나 서는 것의 차이가 아직 작다.** 사거리 우위를 지키며 싸운 판과 그냥 붙어서 싸운 판 사이에 받는 피해가 **분대 전체 체력의 20%p 이상** 벌어져야 한다고 스펙에 적어뒀는데, 실측은 **1.3%p**다. 수치를 어떻게 조합해도 그 격차가 안 나온다는 것까지 재봤고, 미해결로 명시해 뒀다.
- **구석이 너무 안전하다.** 검증용 봇은 출발 지점에서만 버티기 때문에 이 자리를 한 번도 재지 않는다. 실제로는 구석까지 물러나 웅크리면 이긴다. 발견해서 기록만 해둔 상태다.
- **사람이 직접 하는 검증이 비어 있다.** 스펙 §4.5는 처음 하는 사람이 세 판을 하고 세 질문 — 어느 적을 먼저 칠지, 몰리지 않으려면 어디에 설지, 어디서 멈출지 — 에 답하기를 요구한다. **아직 아무도 안 했다.**

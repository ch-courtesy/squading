# 수직 슬라이스 회고 — 왜 이렇게 구현됐나

30초 수직 슬라이스가 11개 task를 모두 통과하고 자동 검증 259건이 green인 상태에서, 사용자가 처음 브라우저를 열었을 때 화면은 빈 보드였고 키 입력은 전혀 먹지 않았다. 재설계를 시작하기 전에 원인을 기록한다.

## 무엇이 잘못됐나

### 1. 기술 검증을 게임보다 먼저 했다

Phaser 2D / Three.js 2.5D / Three.js 3D 세 렌더러 비교에 Task 0~6을 썼다. 결정론 코어와 표시 전용 스냅샷 계약이라는 좋은 자산이 남았지만, 그 시점까지 "이 게임이 재미있는가"에 대한 정보는 0이었다. 성능 비교는 비교할 게임이 있어야 의미가 있는데 순서가 뒤집혔다. `2026-08-14-game-completeness-audit.md`가 "이건 기술 프로토타입이지 게임이 아니다"라고 잡아냈지만 이미 큰 비용이 나간 뒤였다.

### 2. 적대 리뷰가 "구현 가능성"만 물었다

90초 설계는 적대 리뷰에서 구현 불가 판정을 받고 30초 수직 슬라이스로 축소됐다. 리뷰가 던진 질문은 "이 명세로 정확히 구현할 수 있는가"였지 "이게 재미있는가"가 아니었다. 그 결과 제외 목록에 지휘관, 사기, 다중 성장, 병사 개성이 들어갔다 — 정확히 참조 작품을 그 장르로 만드는 요소들이었다. 검증 가능성이 재미를 이겼다.

### 3. 측정 가능한 것만 게이트가 됐다

8-seed 정책 밴드(무입력 0/8, 이동만 0/8, 숙련 6/8)는 "플레이어 입력이 결과를 바꾸는가"를 기계로 증명한다. 훌륭한 지표지만 "그 입력이 재미있는가"는 측정하지 않는다. 그래서 구조 완주가 30틱 연속 무피격을 요구하는 설계처럼, 통계적으로는 에이전시가 있지만 손끝에서는 답답한 규칙이 게이트를 통과했다.

### 4. 사람이 한 번도 플레이하지 않았다

플레이테스트 게이트는 `PENDING(0/3)`인 채로 11개 task가 전부 끝났다. 자동 검증은 계속 green이었다. 사람이 처음 화면을 본 순간 두 가지가 동시에 드러났다.

- **카메라 프레이밍 버그**: 직교 frustum의 `left/right/top/bottom`은 카메라 공간 오프셋인데 월드 좌표를 그대로 대입하고 있었다. lab 시절 스냅샷 중심이 항상 원점이라 우연히 맞았고, 게임플레이 월드가 `0..48 x 0..27`이 된 순간 전 병력이 화면 밖으로 나갔다.
- **한글 IME 입력 버그**: `event.key`는 입력된 문자라서 한글 상태에서 W는 `'ㅈ'`, Q는 `'ㅂ'`로 들어온다. 이동·교대·구조가 전부 무시됐다.

두 버그의 공통 원인은 하나다. **테스트가 실제 사용자 경로가 아니라 코드가 만든 경로를 검증했다.** 렌더러 테스트는 dev 브리지로 씬 그래프 상태만 읽었고 "화면에 보이는가"를 아무도 묻지 않았다. 입력 테스트는 `KeyboardEvent({ key: 'w' })`를 직접 만들어 디스패치했고 실제 입력기 상태를 재현하지 않았다. Playwright도 US 레이아웃으로만 돌았다.

### 5. 도구를 먼저 만들었다

Claude CLI Advisor 스킬 설계·구현·리뷰에 하루가 들어갔다. 그리고 정작 이번 구현 계획 단계에서 Advisor는 허용 태그 없이 `No response requested.`만 반환했고, 계획은 Advisor 승인 없이 진행됐다. 투자 회수가 되지 않았다.

### 6. 명세가 lab을 영구 부채로 만들었다

"Phaser·Three 3D·benchmark 코드를 삭제하지 않고 `?lab=renderers`에서 보존한다"는 제약 때문에 `hybrid-renderer.ts` 하나가 게임과 비교 lab 두 주인을 섬긴다. 디오라마 작업 3개 task가 전부 `snapshot.activeSquad !== undefined` 게이트를 우회로로 써야 했고, 앞으로 렌더러를 건드릴 때마다 같은 세금을 낸다.

## 잘 된 것

버릴 필요가 없는 자산도 분명하다.

- 결정론 계약: 분리된 named PRNG, 정렬·정규화 digest, 14단계 tick 순서, 입력 queue. 재설계에서 그대로 쓴다.
- 8-seed 정책 하네스: 재미를 측정하지는 못해도 회귀는 확실히 잡는다.
- 표시 전용 스냅샷 경계: 렌더러를 세 번 갈아엎는 동안 코어를 한 줄도 건드리지 않았다.
- 리뷰·fix loop: 실제로 결함을 잡았다. `vigor` 강화 시 구조 복귀 HP가 50%가 아니라 62.5%였던 계산 오류, 전멸 화면이 `생존 16`을 출력하던 모순은 모두 리뷰가 잡은 것이다.

## 재설계에 적용할 규칙

1. **재미 가설은 사람 플레이로만 검증한다.** 자동 게이트는 회귀 방지용이지 재미의 증거가 아니다.
2. **모든 단계는 실제 브라우저 1판으로 끝난다.** 스크린샷을 산출물로 남기고, 사람이 안 해본 단계는 완료로 치지 않는다.
3. **사용자 경로를 테스트한다.** 씬 그래프가 아니라 화면에 보이는가(프레이밍·픽셀), 합성 이벤트가 아니라 실제 키 입력(`event.code`, IME 활성 상태 포함)으로 동작하는가.
4. **범위를 깎을 때 "무엇이 빠지면 장르가 사라지는가"를 명시적으로 묻는다.** 구현 난이도만으로 잘라내지 않는다.
5. **밸런스 측정은 설계와 함께 간다.** 규칙을 정한 뒤 측정하는 게 아니라, 측정 가능한 형태로 규칙을 정한다.

# 테이블탑 3렌더러 비교 프로토타입 설계

## 목표

동일한 60~90초 전투 장면을 2D, 2.5D, 실시간 3D로 표현해 실제 화면, 성능과 에셋 제작 비용을 비교한다. 게임을 세 번 만들지 않고 하나의 전투 코어에 세 렌더러를 연결한다. 비교 결과로 최종 렌더러 하나를 선택하고 나머지는 폐기한다.

## 확정된 제품 방향

- 장르: 두 AI 분대를 교대 지휘하는 전장 생존 로그라이트
- 아트: 손으로 칠한 미니어처, 골판지 요새, 나무 블록과 종이 지형의 테이블탑 전쟁
- 분대색: 청록과 주홍
- 구조 신호: 금색 토큰과 수직 빛
- 적군: 채도를 낮춘 자주색 장난감 군세
- 플랫폼: 설치나 로그인 없이 실행되는 브라우저

이 프로토타입은 최종 게임이 아니라 렌더링 기술을 선택하기 위한 수직 비교 실험이다.

## 비교할 세 접근법

### 1. Phaser 2D 가상 디오라마

- 미리 렌더한 미니어처 스프라이트와 2D 골판지 타일을 사용한다.
- 깊이는 Y 정렬, 크기, 가짜 타원 그림자와 레이어로 표현한다.
- WebGL을 우선하고 필요하면 Canvas로 대체한다.
- 가장 빠르고 안정적이며 향후 에셋 제작량을 예측하기 쉽다.

### 2. Three.js 2.5D 혼합

- 바닥, 골판지 벽과 소품은 간단한 3D 메시로 만든다.
- 병사와 효과는 항상 카메라를 향하는 2D 빌보드로 표시한다.
- 제한된 실제 그림자와 고정 직교 카메라로 디오라마 깊이를 강화한다.
- 캐릭터 제작 비용을 2D 수준으로 유지하면서 지형의 입체감을 시험한다.

### 3. Three.js 실시간 3D

- 병사와 적을 저폴리곤 미니어처 메시로 표현한다.
- 반복 캐릭터는 `InstancedMesh`로 묶고 애니메이션은 최소한의 몸체 변형 또는 프레임 상태로 제한한다.
- 고정 직교 카메라와 제한된 조명·그림자를 사용한다.
- 시각적 촉감은 가장 강하지만 모델링, 애니메이션과 성능 위험이 가장 크다.

## 공유 아키텍처

```text
입력
  ↓
결정론적 2D 전투 코어
  ├─ 분대 이동·진형
  ├─ 자동 공격·피격
  ├─ 분대 전환·피로
  ├─ 쓰러짐·구조
  └─ 적 지휘관·사기
  ↓ RenderSnapshot
렌더러 어댑터
  ├─ Phaser 2D
  ├─ Three.js 2.5D
  └─ Three.js 3D
```

3D 렌더러에서도 게임 판정은 2D 평면에서 수행한다. 코어의 `(x, y)`는 Three.js에서 `(x, 0, z)`로 매핑하고, 높이와 그림자는 시각 표현에만 사용한다. 물리, AI, 구조 범위와 공격 판정은 렌더러에 들어가지 않는다.

### 렌더러 계약

```ts
type RenderSnapshot = {
  tick: number
  elapsedMs: number
  units: readonly RenderUnit[]
  projectiles: readonly RenderProjectile[]
  effects: readonly RenderEffect[]
  camera: CameraState
}

type RenderUnit = {
  id: number
  kind: 'commander' | 'soldier' | 'enemy-commander' | 'enemy'
  team: 'teal' | 'scarlet' | 'enemy'
  squad: 'teal' | 'scarlet' | null
  x: number
  y: number
  facingRadians: number
  radius: number
  hp01: number
  fatigue01: number
  morale01: number
  state: 'idle' | 'moving' | 'attacking' | 'downed' | 'rescuing' | 'dead'
}

type RenderProjectile = {
  id: number
  kind: 'friendly' | 'enemy'
  ownerId: number
  x: number
  y: number
  targetX: number
  targetY: number
  progress01: number
}

type RenderEffect = {
  id: number
  kind: 'hit' | 'rescue' | 'morale-break' | 'structure-signal'
  team: RenderUnit['team'] | null
  x: number
  y: number
  startedTick: number
  durationTicks: number
}

type CameraState = {
  centerX: number
  centerY: number
  worldWidth: number
  worldHeight: number
}

interface GameRenderer {
  mount(container: HTMLElement): Promise<void>
  render(snapshot: RenderSnapshot, alpha: number): void
  resize(width: number, height: number, dpr: number): void
  collectMetrics(): RendererMetrics
  dispose(): void
}
```

렌더러는 코어 상태를 수정할 수 없다. 렌더러 전환 시 기존 렌더러를 `dispose`하고 동일한 시드와 시나리오를 처음부터 재생한다.

### 코어 실행 사양

- 코어는 30Hz 고정 타임스텝(`1000 / 30ms`)으로 갱신한다. `requestAnimationFrame` 누적 시간으로 0회 이상 갱신하고 남은 시간의 보간값 `alpha`만 렌더러에 전달한다.
- 시나리오마다 단일 시드 PRNG를 사용하고 코어에서 `Math.random`을 금지한다. 유닛과 이벤트는 안정적인 숫자 ID 순으로 처리한다.
- 결정론 범위는 같은 브라우저 런타임의 같은 코어 빌드다. 렌더러를 바꿔도 같은 입력 로그와 tick의 JSON 직렬화 스냅샷이 같아야 한다.
- 이펙트 생성 tick과 지속 시간은 코어가 소유한다. 렌더러는 종류별 모양만 정하며 생성·삭제 시점을 바꾸지 않는다.
- 자동 벤치마크 입력은 tick별 입력 로그로 고정하고 수동 입력은 별도 모드에서만 기록한다.

## 공통 비교 장면

- 고정 시드와 고정 웨이브 순서
- 지휘관 1명
- 청록 분대 8명, 주홍 분대 8명
- 일반 적 100명으로 시작하고 200명, 300명 부하 모드를 즉시 선택 가능
- 적 지휘관 1명
- 쓰러진 아군 1명과 구조 신호
- 분대 전환, 자동 공격, 피로 표현, 구조, 적 사기 붕괴
- 같은 월드 영역, 화면 점유율, 색상과 효과 타이밍
- 60~90초 동안 자동 재생하거나 사용자가 이동·분대 전환을 직접 수행
- 75초 생존 시 성공, 지휘관과 두 분대가 전투 불능이면 실패하고 양쪽 모두 재시작 버튼 표시

성장 선택, 캠페인, 영구 저장, 완성형 오디오와 다수 병과는 비교 범위에서 제외한다.

자동 벤치마크 모드는 고정 입력 로그를 사용하고 측정·동일 tick 캡처를 유효하게 기록한다. 수동 플레이 모드는 키보드·포인터 조작과 분대 전환 안내를 항상 표시하되 결과와 캡처를 `manual/invalid-for-comparison`으로 표시한다.

## 비교 UI

- 시작 화면에서 `2D`, `2.5D`, `3D`를 즉시 선택한다.
- 렌더러 코드는 동적 `import()`로 분리해 선택한 렌더러와 공통 코어만 로드한다.
- URL의 `?renderer=2d|hybrid|3d&enemies=100|200|300&seed=...`로 조건을 재현한다.
- 화면에는 FPS, p95 프레임 시간, 초기 로드 시간, 활성 유닛 수와 렌더러별 드로우콜을 표시한다.
- 측정 결과를 JSON으로 복사하거나 다운로드할 수 있게 한다.
- 세 렌더러의 스크린샷은 같은 시드와 같은 tick에서 캡처한다.
- 카메라는 같은 `CameraState` 월드 영역을 채우고 지휘관 화면 높이를 기준안의 ±10%로 맞춘다.

## 비교 환경과 품질 단계

- 기준 환경은 구현을 실행하는 개발 Mac의 모델·CPU/GPU·메모리, Chrome 버전, 화면 크기를 비교 보고서에 기록해 고정한다.
- 기준 해상도는 1920×1080, 브라우저 배율 100%, 기기 픽셀 비율 상한 1.5다.
- 모든 수치는 프로덕션 빌드를 새 브라우저 컨텍스트에서 10초 예열한 뒤 60초 동안 측정한다.
- 프레임 시간은 연속 `requestAnimationFrame` 사이의 전체 코어+렌더 시간으로 수집하고 백그라운드 탭 표본은 버린다.
- 기본 품질은 그림자 1024px, 파티클 100%, 기기 픽셀 비율 상한 1.5다.
- 자동 품질 저하는 3초 연속 p95 프레임 시간이 33ms를 넘으면 파티클 50%, 그림자 512px, 기기 픽셀 비율 상한 1.0 순서로 한 단계씩 적용한다.
- 품질 단계 적용 뒤 5초 안정화하고 다음 10초의 p95로 회복 여부를 판정한다.
- Phaser 2D의 가짜 그림자는 위 그림자 해상도 설정의 영향을 받지 않으며, 대신 효과 스프라이트 수를 같은 단계에서 줄인다.
- 초기 로드 시간은 렌더러별 새 브라우저 컨텍스트와 빈 HTTP 캐시에서 선택 시점부터 첫 조작 가능 프레임까지 측정한다.
- Chrome CDP로 렌더러 전환 10회 전후 강제 GC 뒤 JS heap을 측정한다. 증가량 10MB 미만, 잔여 게임 캔버스 0개, 렌더러별 텍스처·지오메트리 카운터가 시작 기준으로 돌아와야 한다. Safari는 기능과 오류 복귀만 확인한다.

## 평가 기준

### 정량 평가

- 초기 화면이 조작 가능해질 때까지 걸린 시간
- 적 100·200·300명에서 평균 FPS와 p95 프레임 시간
- 장시간 실행 후 메모리 증가 여부
- 렌더러를 전환한 뒤 남는 캔버스, 이벤트 리스너와 GPU 자원 여부
- 새 병사 외형 1종을 추가하는 데 걸린 실제 작업 시간

Three.js 드로우콜은 `renderer.info.render.calls`, Phaser는 WebGL renderer의 flush·batch 통계를 사용한다. 엔진별 의미가 다르므로 각 렌더러 내부 최적화 참고값으로만 기록하고 서로 순위를 매기지 않는다.

제작 시간은 같은 작업자가 동일 사양을 구현해 기록하되 학습 순서 효과가 있는 단일 표본임을 보고서에 명시한다. 렌더러별로 완성 게임의 병과 1종에 필요한 스프라이트 상태 수, 메시 수, 텍스처 수, 애니메이션 상태 수와 예상 작업 시간을 함께 외삽한다.

### 정성 평가

각 항목을 1~5점으로 같은 관찰자가 평가한다.

- 지휘관과 두 분대의 즉시 식별
- 쓰러진 병사와 구조 가능 상태의 식별
- 적 지휘관의 식별
- 적 300명에서도 이동 경로와 위험 공간을 읽을 수 있는지
- 손으로 만든 미니어처와 골판지의 촉감
- 공격과 구조 순간의 만족감
- 발표 화면과 스크린샷의 기억성

## 선택 규칙

다음 순서로 최종 렌더러를 선택한다.

1. 깨끗한 브라우저에서 오류 없이 시작하고 핵심 장면을 끝까지 재생해야 한다.
2. 위에 기록한 기준 환경의 기본 품질에서 적 200명일 때 p95 프레임 시간이 20ms 이하여야 한다.
3. 적 300명일 때 p95 프레임 시간이 33ms를 넘더라도 자동 품질 저하 후 33ms 이하로 회복해야 한다.
4. 지휘관, 분대와 구조 대상 가독성 평균이 4점 이상이어야 한다.
5. 통과한 안 중 미니어처 촉감과 발표 효과의 합이 가장 높은 안을 고른다.
6. 5번의 미니어처 촉감+발표 효과 합계(2~10점) 차이가 1점 이하면 제작 비용이 더 낮은 렌더러를 고른다.

세 렌더러가 모두 2번을 통과하지 못하면 공유 코어 최적화 1회와 렌더러별 최대 2시간 최적화만 수행해 재측정한다. 그래도 모두 탈락하면 제출 안전성이 가장 높은 Phaser 2D를 임시 선택하고 미달 수치를 기록한다.

3D는 시각 점수가 근소하게 높은 정도로는 선택하지 않는다. 추가 모델·애니메이션 제작 비용을 정당화할 만큼 분명한 차이가 있어야 한다.

## 실패와 대체 처리

- WebGL을 사용할 수 없으면 2.5D와 3D 선택을 비활성화하고 이유를 표시하며 2D Canvas 대체를 제공한다.
- 에셋 로드가 실패하면 분대색을 유지한 기본 기하 도형으로 대체하고 측정은 유효하지 않다고 표시한다.
- 프록시 에셋은 직접 제작, 사용 조건을 기록한 생성형 도구 제작물 또는 CC0만 사용하고 출처·도구·라이선스를 `docs/assets-license.md`에 기록한다.
- 개별 렌더러 오류는 비교 앱 전체를 중단시키지 않고 선택 화면으로 복귀시킨다.
- 렌더러를 나갈 때 타이머, 입력, 캔버스, 텍스처와 GPU 자원을 모두 해제한다.
- 기기 픽셀 비율 상한, 그림자 해상도, 파티클 수를 단계적으로 낮추는 자동 품질 정책을 사용한다.

## 검증 전략

- Vitest: 같은 시드가 같은 전투 상태와 스냅샷을 만드는지 검증한다.
- 계약 테스트: 세 렌더러가 `mount`, `render`, `resize`, `collectMetrics`, `dispose` 계약을 지키는지 검증한다.
- 계약 테스트는 `dispose` 후 게임 캔버스 0개, 등록 리스너 수의 기준선 복귀, 두 번 호출해도 오류가 없는 멱등성을 단언한다.
- Playwright: 렌더러 선택, URL 재현, 분대 전환, 구조, 시나리오 종료와 오류 복귀를 검증한다.
- 누수 검사: 렌더러 전환을 반복하고 캔버스·리스너 수와 메모리 증가를 확인한다.
- 시각 검토: 같은 tick의 캡처 세 장을 나란히 비교하되 GPU 차이 때문에 픽셀 완전 일치 테스트는 사용하지 않는다.
- 배포 검증: 깨끗한 Chrome과 Safari에서 공개 URL을 연다.

## 구현 순서

0. Vite·TypeScript·Vitest·Playwright 기반과 정적 호스팅 프리뷰를 만든다. 완료 = 빈 비교 셸이 프로덕션 빌드되고 새 브라우저에서 공개 프리뷰 URL로 열린다.
1. 공통 코어와 고정 벤치마크 시나리오를 만든다. 완료 = 같은 시드·입력의 최종 tick 스냅샷 해시가 반복 실행에서 같고 승패·재시작 단위 테스트가 통과한다.
2. Phaser 2D와 측정 UI를 만든다. 완료 = 적 300명 장면, 수동 조작 안내, 성공·실패, JSON 내보내기와 2D 계약 테스트가 작동한다.
3. Three.js 2.5D를 만든다. 완료 = 같은 snapshot fixture를 렌더링하고 동적 import·등가 프레이밍·dispose 계약 테스트가 통과한다.
4. 최소 에셋의 Three.js 3D를 만든다. 완료 = `InstancedMesh` 장면이 같은 fixture를 렌더링하고 3D 계약·프레이밍 테스트가 통과한다.
5. 자동 측정·캡처·비교 보고서·선택을 수행한다. 완료 = 100·200·300명 결과, 같은 tick 캡처, 제작량 외삽, 라이선스, 선택 근거, 공개 URL과 `docs/codex-usage-log.md` 기록이 남는다.

각 렌더러 어댑터와 전용 프록시 에셋은 최대 8 작업시간으로 제한한다. 미완성 항목도 제작 비용과 위험의 증거로 기록한다. 각 렌더러는 앞 렌더러의 완성 에셋을 확장하지 않는다. 파일 형식은 다르지만 지휘관 1종, 아군 2색 1종, 적 1종, 적 지휘관 1종, 골판지 벽 2종과 바닥 1종으로 시각 내용을 맞춘 최소 프록시 세트를 각각 만든다. 2D와 2.5D 캐릭터는 상태당 1개 정지 스프라이트, 3D 캐릭터는 1,500 삼각형 이하와 256px 텍스처 1장으로 제한한다. 최종 선택 전에는 병과 전체나 캠페인용 에셋을 제작하지 않는다.

## 완료 조건

- 하나의 URL에서 세 렌더러를 같은 조건으로 실행할 수 있다.
- 세 렌더러가 동일한 전투 스냅샷과 입력을 사용한다.
- 처음 플레이하는 사람이 안내를 보고 이동·분대 전환을 사용해 성공 또는 실패까지 플레이하고 재시작할 수 있다.
- 적 100·200·300명 측정값과 같은 tick의 캡처가 남는다.
- 정량·정성 점수를 포함한 비교 보고서가 작성된다.
- 선택 규칙에 따라 최종 렌더러 하나와 선택 근거가 기록된다.
